## 슬라이드 1. 표지 (약 25초)
안녕하세요. 1팀의 UNIX시스템프로그래밍 설계과제 **IPC Filter Farm** 발표를 시작하겠습니다. 본 과제는 멀티클라이언트 RGB 이미지 필터 처리 서버를 익명 `pipe`, System V 메시지 큐(`sysv_mq`), System V 공유 메모리+세마포어(`sysv_shm`) 세 가지 IPC로 구현하고, 1단계 기초 측정부터 구현 전 예측, 2단계 응용 실측, 단일 요인 원인 실험, 설계 개선까지 수행해 근거 있는 IPC 선택 기준을 도출한 프로젝트입니다.

## 슬라이드 2. 문제 정의 및 요구사항 (약 40초)
IPC Filter Farm은 여러 클라이언트가 동시에 요청하는 RGB 이미지에 서버가 `GRAY`, `BLUR`, `EDGE` 필터를 적용해 돌려주는 병렬 처리 서버입니다. 한 변이 64px에서 2048px까지 커지면 편도 페이로드가 12KiB에서 12MiB까지 1,024배 변하기 때문에, 작은 이미지의 고정 비용과 큰 이미지의 복사·청크 분할·동기화 비용이 극명하게 대비됩니다. 서버는 기본 5스레드, 클라이언트는 4스레드로 구성했고, 2클라이언트 1,000장 비순차 처리에서 오류 0건과 공정성 규칙 R1~R7을 충족하도록 설계했습니다.

## 슬라이드 3. 1단계 IPC 기초 측정 — 환경과 설계 (약 35초)
모든 정식 측정은 팀 공통 Ubuntu 24.04 네이티브 서버(Xeon Bronze 3106 16코어, 62.4GiB, Linux 6.8.0-149, GCC 13.3)에서 클린 빌드 로그와 바이너리 해시를 함께 기록해 수행했습니다. 1단계에서는 필터 없이 바이트만 왕복하는 `basic_server`·`basic_client`로 64B부터 1MiB까지 5개 크기, 클라이언트 1~8개, 지연 `W=1`과 처리량 `W=4` 조합 360회, 총 135만 표본을 수집했습니다. 시간은 `CLOCK_MONOTONIC`으로 측정했고, 워밍업 100회 이후 경계 시점에 `getrusage()`와 `VmRSS`를 기록했습니다.

## 슬라이드 4. 1단계 IPC 기초 측정 — 결과와 해석 (약 50초)
왼쪽 그래프는 `W=1` 왕복 지연, 오른쪽은 `W=4` 단방향 유효 처리량입니다. 예상과 달리 `W=1` 지연에서는 전 크기에서 `pipe`가 가장 낮았고(`64B` 303µs, `1MiB` 14.0ms), `sysv_mq`와 `sysv_shm`은 종료 응답성을 위한 1ms 비차단 재시도(`ipc_nap`) 영향으로 64B·1KiB에서 1.1~1.2ms대를 보였습니다. 반면 `W=4` 처리량에서는 256KiB와 1MiB 사이에서 순위가 역전되어, 1MiB에서 `sysv_shm`이 367.0MB/s로 `pipe`(251.3MB/s)의 1.46배, `sysv_mq`(14.7MB/s)의 25배를 기록했습니다. 1MiB `W=4`에서 `sysv_shm`의 `sys CPU`는 156.5ms로 압도적으로 낮았고, `sysv_mq`는 8,000B 청크 분할과 16KiB 큐 제약 때문에 `sys CPU` 9.4초와 자발적 전환 24.8만 회가 발생했습니다.

## 슬라이드 5. 워크로드 명세와 성능 예측 (약 40초)
2단계 응용은 편도 `48B + 3×size²` 바이트를 N:1 요청·ID별 응답으로 주고받는 폐루프 파이프라인 구조입니다. 과제 원칙에 따라 구현 전 작성한 예측 원문을 그대로 보존했으며, 최초 1단계 실측 직후·응용 측정 전에 보완한 11월 13일 기록을 별도로 구분했습니다. 원문에서는 대형 GRAY 처리량을 `SHM > pipe > MQ`로 예측했고, 보완에서는 소형 이미지는 `pipe` 우세, `512²` 단일 요청은 역전 구간 사이로 미확정이라 명시했습니다.

## 슬라이드 6. 시스템 설계 — 프로세스·스레드 아키텍처 (약 35초)
시스템 구조는 클라이언트 4스레드(`main`, `sender`, `receiver`, `stats`)와 서버 5스레드(`main`, `receiver`, `worker 1..N`, `responder`)로 이루어집니다. 핵심은 응용 로직을 100% 공통으로 유지하고 가운데 `ipc_backend_t` 6함수 인터페이스만 `pipe`, `sysv_mq`, `sysv_shm`으로 교체하는 구조입니다. 이를 통해 백엔드별 코드 분기(R7 위반) 없이 공정하게 성능을 비교할 수 있습니다.

## 슬라이드 7. 시스템 설계 — 스레드 및 공유 자원 동기화 (약 40초)
서버의 `jobs`와 `done` 유계 링은 `mutex`와 `not_full`/`not_empty` `condvar`로 보호하며, 작업 포인터 소유권을 이전해 필터 연산 중에는 락을 잡지 않습니다. `permits`와 `inflight` 세마포어로 메모리 상한과 미완료 요청 수를 제어하고, `sysv_shm`은 `empty → memcpy → full` 순의 SysV 세마포어와 `fcntl` 메타 파일 레코드 잠금으로 슬롯 훼손과 상대 사망을 안전하게 처리합니다. 모든 대기는 100ms 유한 대기로 `g_stop`을 확인하고, 종료 시 `bq_close`가 양쪽 조건변수를 깨워 교착과 무한 대기를 차단합니다.

## 슬라이드 8. 구현 내용 — IPC 3종 핵심과 회귀 검증 (약 35초)
`pipe`는 `pipe_run`이 클라별 요청·응답 FD를 생성해 `fork/exec`로 상속하고 non-blocking `poll`로 부분 전송과 `EPIPE`를 처리합니다. `sysv_mq`는 요청(60010)·응답(60011) 큐를 분리해 8,000B 청크를 ID당 최대 `W`개 슬롯으로 재조립합니다. `sysv_shm`은 60012·60013 키로 클라별 링을 분리합니다. `make` 전체 빌드와 6개 개별 빌드 모두 경고 0으로 통과했고, 2026년 11월 19일 Ubuntu 24.04에서 24단계 전체 회귀와 초안 tar 해제 빌드 검증까지 완료했습니다.

## 슬라이드 9. 구현 내용 — 2클라 데모·`strace`·`ipcs` 확인 (약 45초)
256² 이미지로 클라이언트 1은 GRAY, 클라이언트 2는 EDGE를 동시에 100장씩 요청한 실제 Linux 데모 결과입니다. 화면의 4개 이미지는 실제 PPM 결과를 변환한 전후 비교이며, 독립 Python 참조 필터와 전 바이트 일치, `mismatches=0`, 합산 585.6 images/s를 기록했습니다. 종료 직후 `ipcs -q -m -s` 결과에서 본인 소유 MQ·SHM·SEM이 모두 0건임을 확인했고, 오른쪽 `strace` 비교에서 `sysv_mq`의 52,865회 호출과 `clock_nanosleep` 급증을 확인했습니다.

## 슬라이드 10. 성능 분석 — 2단계 S1 이미지 크기별 지연 및 CPU (약 45초)
2단계 S1(`W=1`, 클라 1, GRAY) 실측 결과입니다. 64²에서는 `pipe`가 905.6 img/s(`p50 535µs`)로 가장 빨랐고, `80²` 이상에서 MQ가 크게 뒤처졌습니다. `512²`(69.6 vs 59.9)와 `1024²`(20.6 vs 20.0)에서는 `pipe`가 근소하게 앞섰으나, `2048²`(12MiB)에서는 `sysv_shm`이 7.10 img/s로 `pipe`(6.53)를 8.8% 추월했습니다. 오른쪽 `512²` CPU 그래프에서 `sysv_shm`은 `sys CPU`가 744ms로 `pipe`(3,779ms)의 1/5, `sysv_mq`(9,656ms)의 1/13 수준입니다.

## 슬라이드 11. 성능 분석 — S2 클라 수 · S3 필터 · S4 파이프라인 (약 45초)
S2, S3, S4 결과입니다. S2에서 클라이언트가 4개로 늘어나면 `sysv_shm`이 362.0 img/s로 `pipe`(309.0)를 17.2% 앞서고, S4 파이프라인 `W=4`에서는 408.5 img/s로 17.8% 앞섭니다. `W=16`에서는 `SHM`이 467.6 img/s까지 오르지만 `p99`가 3.6배(43.0ms), RSS가 60MiB로 급증해 지연·메모리 균형점은 `W=4`였습니다. 한편 S3에서 무거운 `EDGE` 필터로 가면 `pipe`(55.03)와 `SHM`(54.99) 차이가 0.07%까지 줄어, 연산 병목이 IPC 차이를 사실상 없앰을 확인했습니다.

## 슬라이드 12. 성능 분석 — 예측 대조 및 S5 단일 요인 원인 실험 (약 45초)
예측과 실측을 대조하면 소형 `pipe` 우세, S3 희석, S4 트레이드오프는 일치했고, S2에서는 파이프라인 유휴 해소 덕분에 예상보다 큰 초선형 증가가 나타났습니다. 특히 `sysv_mq`의 극심한 저하가 큐 백프레셔 때문인지 확인하기 위해 오른쪽 S5 단일 요인 실험을 수행했습니다. 청크 크기 등 모든 조건을 고정하고 `kernel.msgmnb`만 16KiB에서 64KiB로 4배 늘리자 처리량이 2.13에서 6.63 img/s로 **3.11배** 뛰고, `p99`는 66.3%, 자발적 전환은 70.3% 감소해 백프레셔 병목을 실증했습니다.

## 슬라이드 13. 설계 개선 전후 비교 및 최종 IPC 선택 가이드라인 (약 45초)
설계 개선으로 이웃 픽셀 참조가 없는 GRAY 필터에 입력 버퍼를 출력으로 재사용하는 `--inplace-gray`를 구현해 512²·2클라·`W=4`에서 전후 비교했습니다. 종료 RSS 합계는 세 IPC 모두 7.9%에서 11.4%까지 줄어 메모리 절감 효과를 확인했지만, 처리량은 오히려 소폭 낮아지고 반복 범위가 겹쳐 속도 개선 방안으로는 채택하지 않았습니다. 종합하면 본 이미지 필터 서버의 기본 IPC는 대형·고동시성에 강한 **`sysv_shm` (`W=4`)**이 적합하며, 256² 이하 소형이나 단일 저지연 워크로드에는 **익명 `pipe`**가 유리합니다.

## 슬라이드 15. 결론 및 생성형 AI 활용·오류 검증 (약 40초)
결론적으로 "공유 메모리가 항상 가장 빠르다"는 일반론은 실측과 달랐고, 페이로드 크기·동시성·연산 비중에 따라 최적 IPC가 달라짐을 534회 재측정 데이터로 재확인했습니다. 마지막으로 생성형 AI 활용에서는 모든 수치를 직접 실측했으며, AI가 작성한 코드에서 두 가지 결함을 찾아 수정했습니다. 첫째, `server.c`의 `respond()`에서 정상 워밍업 응답이 실패 분기로 빠질 수 있던 로직을 분리했고, 둘째, `resource.c`의 macOS 컴파일 오류 4건을 `#ifdef __linux__` 가드로 해결해 양 OS와 Linux 회귀·정식 재측정을 모두 통과했습니다. 이상으로 발표를 마치겠습니다. 감사합니다.

# UNIX시스템프로그래밍 설계과제 안내문

## 1. 과제 개요와 목표

설계과제 명(공통 주제): 내 응용에 맞는 IPC는 무엇인가 — 예측하고, 구현하고, 검증하라

이번 설계과제는 팀이 직접 기획한 응용 프로그램에 가장 적합한 IPC 기법을 근거를 갖고 선택하는 것이 목표입니다. pipe, message queue(message passing), shared memory 3가지 버전을 구현하는 것은 출발점일 뿐이며, 평가의 중심은 측정 결과를 해석하고 설계를 개선하는 과정에 있습니다.

과제는 두 단계로 진행합니다.

1. 1단계 — IPC 기초 성능 측정(공통): 팀에서 구현에 사용한 컴퓨터에서 3가지 IPC의 기본 특성(지연시간, 처리량)을 측정하고 해석합니다.
2. 2단계 — 팀 응용 설계와 검증: 응용의 통신 특성(워크로드)을 정의하고, 1단계 결과를 근거로 어떤 IPC가 유리할지 예측한 뒤, 3가지 버전을 구현·측정하여 예측과 실제의 차이를 분석하고 설계를 개선합니다.

이 과제를 통해 학생은 다음을 할 수 있어야 합니다.

- 3가지 IPC 기법의 동작 원리와 성능 특성(데이터 복사, 시스템 콜, 동기화 비용)을 설명할 수 있다.
- 측정 목적에 맞게 성능 측정 방법을 설계하고, 측정값을 통계적으로 정리할 수 있다.
- 멀티스레드 환경에서 경쟁 상태가 생기지 않도록 동기화를 설계하고, 그 선택의 이유를 설명할 수 있다.
- 측정 결과를 근거로 자기 응용에 맞는 IPC를 선택하고 설계를 개선할 수 있다.

| -------------- | ----------- | --------------------------------------------------- |
| e-class 참조 | 팀 구성   | e-class에 팀명, 팀장, 팀원 등록                   |

권장 진행 일정

중간 제출물은 없지만, 아래 순서를 지켜야 "예측 → 검증" 구조가 제대로 성립합니다. 특히 2단계 예측은 반드시 구현 전에 작성해야 합니다.


| 주차  | 진행 내용                                                                       |
| ------- | --------------------------------------------------------------------------------- |
| 1주차 | 팀 구성, Linux 환경 구축과 측정용 컴퓨터 결정, 1단계 벤치마크 구현과 측정·해석 |
| 2주차 | 응용 기획, 워크로드 명세, IPC 성능 예측 작성 → 3가지 버전 구현 시작            |
| 3주차 | 구현 완료와 동기화 검증, 응용 성능 측정, 예측 대비 원인 분석, 설계 개선         |
| 4주차 | 개선 전후 비교, 최종보고서·발표자료 작성, 발표 동영상 녹화 및 제출             |

- 3인 1조로 수행하며, 팀 구성은 e-class를 통해 합니다.
- 팀원 3명은 pipe, message queue, shared memory 버전을 각각 1개씩 맡아 구현합니다.
- 팀원이 1~2명인 경우 pipe와 Advanced IPC(message queue 또는 shared memory) 중 하나, 총 2가지 버전을 구현합니다.
- 1단계 기초 측정과 2단계 성능 분석은 팀원 모두가 함께 수행합니다. 각자 맡은 버전만 측정하는 것이 아니라, 모든 버전을 같은 컴퓨터에서 측정해야 합니다.

## 3. 1단계: IPC 기초 성능 측정 (공통)

1단계의 목적은 팀에서 구현에 사용한 컴퓨터에서 각 IPC가 어떤 특성을 보이는지 직접 확인하는 것입니다. 응용 기능 없이 데이터만 주고받는 간단한 벤치마크 프로그램을 3가지 IPC로 각각 작성합니다.

측정 항목

- 왕복 지연시간(ping-pong): 클라이언트가 메시지를 보내고 서버가 같은 크기로 응답할 때까지 걸리는 시간
- 처리량(throughput): 일정 시간 동안 또는 일정 양의 데이터를 보낼 때 초당 전송 메시지 수와 초당 전송 바이트 수

변인

- 메시지 크기: 최소 5단계 이상 (예: 64B, 1KB, 16KB, 256KB, 1MB)
- 동시 클라이언트 수: 1, 2, 4, 8
- 위 범위는 최소 기준이며, 팀이 의미 있다고 판단하면 범위를 넓히거나 변인을 추가할 수 있습니다.

최종보고서에 포함할 내용

- 측정 환경 (CPU, 코어 수, 메모리, OS·커널 버전, gcc 버전, 가상화 여부)
- 메시지 크기별, 클라이언트 수별 그래프 (3가지 IPC를 한 그래프에서 비교)
- 결과 해석: 어느 조건에서 어떤 IPC가 유리했는지, 순위가 뒤바뀌는 지점이 있었는지, 그 이유는 무엇이라고 보는지

교과서적 결론("shared memory가 가장 빠르다")을 그대로 쓰는 것이 아니라, 팀에서 구현에 사용한 컴퓨터에서 나온 숫자를 근거로 설명해야 합니다. 예상과 다른 결과가 나왔다면 그것이 오히려 좋은 분석 대상입니다.

## 4. 2단계: 팀 응용 설계와 검증

2단계에서는 팀이 기획한 응용을 3가지 IPC로 구현하고, 1단계 결과로 세운 예측이 실제 응용에서도 맞는지 검증합니다.

수행 절차

1. 응용 기획: 클라이언트-서버 구조의 응용 프로그램을 기획합니다(아래 주제 조건 참고).
2. 워크로드 명세: 응용의 통신 특성을 정량적으로 정의합니다.

   - 메시지 종류와 크기(분포), 요청 빈도
   - 통신 패턴 (1:N, N:1, 요청-응답, 파이프라인 등)
   - 서버 공유 자료구조에 대한 읽기/쓰기 비율
3. 예측(구현 전): 1단계 결과와 워크로드 명세를 근거로 "우리 응용에서는 어떤 조건에서 어떤 IPC가 유리할 것"이라고 예측하고, 그 이유를 씁니다. 예측은 반드시 구현과 측정 전에 작성하고, 최종보고서에 작성 당시 내용 그대로 포함합니다.
4. 구현: 같은 응용을 3가지 IPC 버전으로 구현합니다. 응용 로직은 공통 모듈로 분리하고 IPC 부분만 버전별로 다르게 작성하기를 권장합니다.
5. 검증: 같은 컴퓨터에서 3가지 버전을 측정하고, 예측과 실제를 비교합니다. 예측이 틀린 부분은 원인을 근거와 함께 분석합니다. 원인으로 추정한 요인은 그 요인만 바꾼 추가 실험으로 확인합니다(예: 락 범위만 바꿔서 다시 측정, 버퍼 크기만 바꿔서 다시 측정).
6. 설계 개선: 분석 결과를 바탕으로 최소 1회 이상 설계를 개선하고, 개선 전후를 측정하여 비교합니다. (예: 락 범위 축소, 버퍼 크기 조정, 메시지 묶음 전송, 데이터 복사 횟수 감소)

응용 주제 조건

- IPC 선택이 성능에 영향을 줄 만큼 데이터 양이나 통신 빈도가 의미 있는 응용일 것
- 서버에 여러 스레드가 함께 접근하는 공유 자료구조가 있을 것
- 클라이언트는 2개 이상 동시에 실행할 수 있을 것
- 단순 채팅 서버, 단순 메시지 중계(받은 메시지를 그대로 다른 클라이언트에 전달만 하는 구조)는 주제로 인정하지 않음

응용 주제 예시 (예시일 뿐이며, 팀 고유의 아이디어를 권장합니다)


| 응용 예시                             | IPC 관점에서 분석할 점                          |
| --------------------------------------- | ------------------------------------------------- |
| 이미지 필터 처리 서버 (흑백, 블러 등) | 큰 데이터 전송에서 데이터 복사 비용의 차이      |
| 로그 수집·통계 서버                  | 작은 메시지가 대량으로 들어올 때 시스템 콜 비용 |
| 좌석·강의실 예약 시스템              | 동시 예약 충돌과 동기화 설계                    |
| 센서 데이터 집계 서버                 | N:1 패턴에서 버퍼 크기와 처리량의 균형          |
| 파일 압축·암호화 작업 서버           | 요청과 응답 크기가 비대칭인 통신                |
| 작업 큐 기반 연산 서버 (행렬 연산 등) | 작업 분배와 결과 수집 패턴                      |

## 5. 측정 방법 필수 요건

1단계와 2단계 모두 아래 요건을 지켜야 하며, 보고서에 측정 방법을 구체적으로 기술해야 합니다.

- 시간 측정: clock\_gettime(CLOCK\_MONOTONIC, ...)을 사용합니다. 타임스탬프를 코드의 어느 지점에서 찍었는지 명시하고, 그 위치를 선택한 이유를 설명합니다.
- 반복 측정: 워밍업 실행 후 측정하며, 각 조건마다 충분히 반복합니다(최소 30회 이상 권장). 평균과 함께 **중앙값, 최대값(또는 상위 99%)**을 보고합니다.
- 지연시간과 처리량 구분: 두 지표를 구분해서 측정하고, 어느 지표가 응용에 더 중요한지 설명합니다.
- 자원 사용량: getrusage()로 CPU 시간과 컨텍스트 스위치 횟수(자발적/비자발적)를, /proc/self/status(VmRSS 등)로 메모리 사용량을 측정합니다.
- 측정 간섭 최소화: 측정 구간 안에서 printf 같은 출력을 피하고, 측정 중에는 다른 무거운 프로그램을 종료합니다. 측정 코드 자체가 결과에 주는 영향을 고려합니다.
- 원인 분석 근거: 성능 차이의 원인을 "그럴 것이다"가 아니라 근거로 설명합니다. 필요하면 strace -c(시스템 콜 횟수), /usr/bin/time -v, 동기화 대기 시간 측정 등을 활용합니다.
- 원자료 보존: 측정 원자료(CSV 등)와 측정 스크립트를 제출물에 포함하여, 같은 실험을 다시 수행할 수 있게 합니다.

## 6. 현실적 제한 요건과 실행 환경

현실적 제한 요건

- 병행 처리에 따른 경쟁 상태(race condition)가 발생하지 않도록 적절한 동기화 기법을 사용하고, 어떤 동기화 기법을 왜 선택했는지 설명할 것
- 성능을 높이는 방안과 메모리 사용량을 줄이는 방안을 고려하여 설계하고, 그 효과를 측정으로 확인할 것
- 표준 UNIX(POSIX) 환경의 개발 도구와 API를 사용하고, make 유틸리티를 필수로 사용할 것
- 클라이언트와 서버 모두 프로세스별 최소 3개 이상의 스레드를 사용할 것
- 프로그램이 종료될 때 생성한 IPC 자원(message queue, shared memory, semaphore)을 정리할 것. 실행 후 ipcs 명령으로 남은 자원이 없는지 확인한 결과를 보고서에 포함합니다.

실행 환경

- 팀에서 구현에 사용한 컴퓨터의 Linux 환경에서 개발과 측정을 수행합니다. Linux 네이티브 설치, 가상머신(VirtualBox, VMware 등), WSL2 모두 허용합니다.
- macOS는 POSIX message queue를 지원하지 않는 등 차이가 있으므로, macOS 사용자는 Linux 가상머신을 사용하기 바랍니다.
- 3가지 버전의 측정은 반드시 같은 컴퓨터에서 수행해야 합니다. 팀원이 각자 구현하더라도 측정은 한 대의 컴퓨터에서 모아서 진행합니다.
- 보고서에 측정 환경(CPU 모델, 코어 수, 메모리, OS 배포판과 커널 버전, gcc 버전, 가상화 여부)을 기록합니다.
- 채점 시에는 Ubuntu Linux + gcc 환경에서 make로 컴파일하여 실행을 확인합니다.

Advanced IPC key 부여 원칙

- System V IPC를 사용하는 경우 key 번호는 60xxy로 부여합니다. xx는 팀 번호, y는 0~9 중 선택합니다. (예: 11조 → 60110 ~ 60119)
- POSIX IPC를 사용하는 경우 이름을 /osproject\_조번호\_용도 형식으로 부여합니다. (예: /osproject\_11\_queue)

## 7. 생성형 AI 활용 규정

ChatGPT, Claude, Gemini, Copilot 등 생성형 AI를 자유롭게 활용할 수 있습니다. 응용 아이디어 도출, 코드 작성, 디버깅, 개념 학습, 그래프 작성 등 어느 단계에서 사용해도 됩니다. 다만 다음을 지켜야 합니다.

- 측정 데이터는 반드시 직접 측정한 값이어야 합니다. AI가 제시한 수치나 일반적인 성능 비교 결과를 측정값처럼 사용하면 안 됩니다.
- 최종보고서에 AI를 어느 단계에서, 어떻게 활용했는지 구체적으로 기술합니다(주요 프롬프트 예시 포함). 주요 AI 대화 기록(대화 내보내기 파일 또는 캡처)은 최종보고서 부록으로 첨부합니다.
- AI의 제안이나 설명이 틀렸거나 우리 측정 결과와 맞지 않았던 사례를 최소 2개 기술하고, 어떻게 확인하고 바로잡았는지 설명합니다.
- AI가 생성한 코드에서 발견한 문제(경쟁 상태, 교착 상태, IPC 자원 미해제, 오류 처리 누락 등)가 있다면 함께 기술합니다.

## 8. 제출물, 제출 방법, 평가

제출물

- 최종보고서 (제출일 e-class 참조): 제시된 최종보고서 서식에 따라 작성
- 소스 파일: tar cvf osproject\_조번호.tar 명령으로 하나의 tar 파일로 묶어 제출
- 발표자료(PPT)와 발표 동영상

tar 파일에 포함할 내용

- Makefile: 1단계 벤치마크와 2단계 응용의 각 버전을 별도로 컴파일할 수 있어야 하며, make로 한 번에 전체 컴파일도 가능해야 함
- readme.txt: 실행 환경, 컴파일 방법, 실행 방법, 측정 재현 방법
- C 소스 파일과 헤더 파일
- 측정 스크립트와 측정 원자료(CSV 등)

제출 방법

평가 방법


| 평가 항목                             | 비중 |
| --------------------------------------- | ------ |
| 1단계 기초 측정과 해석                | 15%  |
| 워크로드 명세와 예측의 근거           | 15%  |
| 구현 (버전별 동작, 동기화 설계, make) | 25%  |
| 예측 대비 실측 비교 분석과 원인 규명  | 25%  |
| 설계 개선과 전후 비교                 | 10%  |
| 생성형 AI 활용 기록, 발표 동영상      | 10%  |

구현 자체보다 측정 결과의 해석과 근거 있는 설계 판단에 높은 비중을 둡니다. 3가지 버전이 모두 잘 동작하더라도 분석이 일반론에 그치면 높은 점수를 받기 어렵습니다. 일반적인 IPC 특성 설명(교재나 AI가 제시하는 일반론)에는 점수를 주지 않으며, 팀이 직접 측정한 특정 수치를 근거로 한 설명과 추가 실험으로 확인한 원인만 분석 점수로 인정합니다.

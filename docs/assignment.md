# 과제 요약 — IPC Filter Farm

[문서 안내](../README.md#관련-문서)

UNIX시스템프로그래밍 설계과제(**내 응용에 맞는 IPC는 무엇인가 — 예측하고, 구현하고, 검증하라**)의 핵심 요약이다. 상세 원본은 [과제 안내문](assignment-guide.md)과 [최종보고서 서식](final-report-template.md)이며, 프로젝트별 설계는 [요구사항](01-func/01-requirements.md)을 따른다.

## 일정과 팀 구성

- 3인 1조 기준 `pipe`, `message queue`, `shared memory`를 1명씩 담당한다(1~2인 팀은 `pipe` + Advanced IPC 1종).
- 기초 측정과 응용 분석은 팀 공통 머신 1대에서 공동 수행한다([팀 설정](01-func/01-requirements.md#실행-인터페이스)).

## 필수 수행 순서

구현 전 예측 작성과 원문 수록은 [과제 안내문](assignment-guide.md)의 일정·응용 요구사항과 [보고서 서식](final-report-template.md)의 3.2절에서 정한 원본 과제 조건이다. 해시 생성·동결 디렉터리·특정 스크립트 사용은 원본 제출 조건이 아니다.

| 단계 | 핵심 요구 |
| --- | --- |
| 1. 기초 측정 | 필터 없는 바이트 왕복 벤치마크(크기 5단계 이상: 64B·1KB·16KB·256KB·1MB, 클라 1·2·4·8, RTT·메시지/s·바이트/s) |
| 2. 워크로드·예측 | 메시지 크기 분포·요청 빈도·통신 패턴·공유 자료구조 읽기/쓰기 비율·동시 클라 수 정량화 후 **응용 구현·측정 전 예측 원문 보존** |
| 3. 응용 구현·검증 | 동일 응용(서버 공유 자료구조 + 동시 클라 2개 이상, 단순 중계 불가)을 IPC별로 구현 |
| 4. 분석·개선 | 예측·실측 비교, 단일 요인 원인 실험, 최소 1회 설계 개선 전후 비교 및 최종 IPC 선택 |

## 공통 측정·구현 조건

- 계측: `clock_gettime(CLOCK_MONOTONIC)`, 워밍업 후 반복(30회 이상 권장), 평균·중앙값·최대 또는 p99, `getrusage()`(CPU·컨텍스트 스위치), `/proc/self/status`(`VmRSS`), 필요 시 `strace -c`·`/usr/bin/time -v` 보조.
- 구현: 서버·클라 각 **최소 3개 스레드**, 동기화 근거 명시, 표준 UNIX/POSIX API + `make`, Ubuntu Linux + gcc 기준 채점, 종료 시 IPC 정리 및 `ipcs` 캡처.
- 식별자: SysV key `60xxy`(`xx`=팀 번호, `y`=0~9), POSIX 이름 `/osproject_조번호_용도`.
